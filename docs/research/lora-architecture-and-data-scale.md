# YuE2 ボーカルLoRA — アーキテクチャ・学習規模・必要データ量

「特定話者の歌声に似せる」という目的に対して、**どこに何パラメータのLoRAを差し、
何時間のデータで、何ステップ回すのか**を具体的な数値まで落とした設計文書。

> **本プロジェクトの確定制約**
> - 対象話者の歌声データは **4〜6曲・合計約10分で固定(追加取得不可)**
> - 実行環境は **ローカルの Windows + RTX 4090(24GB)が主**。クラウドは M5 の並列生成のみ
>   ([implementation-milestones.md](implementation-milestones.md) の実行環境節)
>
> §1〜§4.6 は一般論、**§4.7 と §5.2 がこの制約下での実際の設計**。
> 一般論の推奨値(30〜60分・r=32)をそのまま適用しないこと。
> 実行計画は [implementation-milestones.md](implementation-milestones.md) の M0〜M6。

前提となる調査結果(公式に参照音声機能が無いこと、コミュニティ実装の実測値)は
[yue2-voice-cloning-feasibility.md](yue2-voice-cloning-feasibility.md) と
[community-implementations.md](community-implementations.md) に、
フェーズ計画と予算配分は [custom-training-plan.md](custom-training-plan.md) にある。

## 0. 前提 — 目的・成果物・数値の出所

### 0.1 成果物(2026-09-18 合意)

**学習コード + アダプタ重み**。生成した楽曲だけでは完了としない。

この決定には2つの帰結がある。

1. **G0.5(参照音声ICL注入)が効いても、それだけでは完了しない。** ICLは学習を伴わないので
   重みが残らない。重みを成果物にするなら §5.2 のゲート A / B は回す必要がある
2. **再現性と可搬性が要件に入る。** 学習コードは他者(将来の自分を含む)が回せる形にする。
   シード固定・設定のシリアライズ・潜在キャッシュの再生成手順まで含む
   ([custom-training-plan.md](custom-training-plan.md) §6.2 の再現性の作り込みを壊さないこと)

達成条件は **§6(operating envelope)** に確定させてあり、**そのまま model card の動作範囲になる。**

### 0.2 数値の出所の区別

本文書には性質の異なる3種類の数値が混在するので、必ずラベルで区別する。

| ラベル | 意味 |
|---|---|
| **[コード]** | 本リポジトリのソースから直接読み取った、または `config` 既定値から解析的に計算した確定値 |
| **[実測]** | コミュニティ実装の公開されている実測値(再現はしていない) |
| **[推定]** | 本文書で類似システムからの類推・FLOPs計算で見積もった値。実測ではない |

## 1. 結論 — どこまで「似る」のが現実的か

「似ている」を一段階の話にすると判断できないので、3レベルに分解する。

| Lv | 何が似るか | 手段 | 必要データ | 到達見込み [推定] |
|---|---|---|---|---|
| **1** | 歌い方・発音・ビブラート・フレーズ末の癖。声質は「別人だが歌い回しが寄る」 | **AR branch LoRA**(semantic token 側) | 10〜30分 | **高い。** AR側は既にコミュニティに動く学習系がある。日本語ディクションの改善もここ |
| **2** | 声質が「同系統」になる。性別・声域・明暗・ざらつきが一致し、初見では「この歌手っぽい」と感じる | **NAR branch LoRA**(per-voice、対象話者に過学習させる) | 30〜60分 | **中。** 構造上は可能。ただし公式学習コードが無く、フローマッチング損失の再実装が成否を決める |
| **3** | 話者照合で本人と判定される(`wespeaker-voxceleb-resnet34-LM` コサインで本人内分布に入る) | **NARに音色条件付け経路を新設** + Lv2 | 2〜3時間(単一話者)/ 100時間級(汎化) | **低〜中。** $500〜1000 の範囲では「たまに刺さる」止まりの可能性が高い。ここを最終目標に据えると期待値を外す |

**現実的な狙いどころは Lv2 + Lv1 の組み合わせ。** Lv3 は参照音声ICL注入(§5.2 の G0.5 =
[implementation-milestones.md](implementation-milestones.md) の **M2**)が
効いた場合のみ視野に入る。詳細は §5 の判断ゲート。

**この表は対象話者データ30〜60分が前提。** 本プロジェクトの実条件(10分固定)では
Lv2 が「中の下」に下がり、かつ**条件付きの達成**として定義し直す必要がある(§4.7.7)。

### 1.1 なぜ Lv3 が難しいのか(構造的理由)

`CODEC_SIZE = 32768` @ 25 Hz の semantic token は **log2(32768) × 25 = 375 bps** しか
情報を運べない [コード: `protocol.py:10`, VAE `downsampling_ratio=1920` / `sample_rate=48000`]。
話者性は semantic token を通らず、**NAR branch が AR hidden states と事前分布から生成している**。
つまり「音色を指定する」には NAR 側に新しい入力経路を作るしかなく、それが公式にもコミュニティにも
存在しない。LoRA だけでは「NARが持っている音色分布を偏らせる」ことしかできない。

## 2. アーキテクチャ

### 2.1 3.58B の内訳 [コード]

`YuE2Config` 既定値 (`modeling_yue2.py:79-96`):

```
hidden_size H = 2048        num_hidden_layers L = 28
num_attention_heads = 16    num_key_value_heads = 8    head_dim = 128
intermediate_size I = 6144  vocab_size V = 184704      latent_dim D = 64
max_position_embeddings = 24576   timestep_shift = 1.0
```

`DecoderLayer` は Mixture-of-Transformers で、AR と NAR が**完全に別の重み**を持つ
(`modeling_yue2.py:227`)。Q/K/V/O と gate/up/down が二重、layernorm も二重。

| ブロック | 1層あたり | 28層合計 | 全体比 |
|---|---:|---:|---:|
| attention (q 4.19M + k 2.10M + v 2.10M + o 4.19M) | 12.58M | 352M | 9.8% |
| MLP (gate/up/down 12.58M ずつ) | 37.75M | 1,057M | 29.5% |
| **1 branch 小計** | **50.33M** | **1.409B** | **39.4%** |
| AR branch | | 1.409B | 39.4% |
| NAR branch | | 1.409B | 39.4% |
| `embed_tokens` (184704×2048) | | 378.3M | 10.6% |
| `lm_head` (`tie_word_embeddings=False`) | | 378.3M | 10.6% |
| `vae2llm`(64→2048) + `llm2vae`(2048→64) + `TimestepEmbedder` | | 4.98M | 0.14% |
| **合計(解析値)** | | **3.580B** | 100% |

**重要な帰結**: 声を扱う NAR branch は全体の 39.4% = 1.409B しかない。
ここだけを対象にすれば、3B級モデルを丸ごと触るより遥かに軽い。

### 2.2 LoRAをどこに差すか

| 目的 | 対象モジュール | 層数 × 行列数 |
|---|---|---|
| **Lv1: 歌い方・日本語ディクション** | `self_attn.{q,k,v,o}_proj` + `mlp.{gate,up,down}_proj` | 28 × 7 = 196 |
| **Lv2: 声質** | `nar_self_attn.{q,k,v,o}_proj` + `nar_mlp.{gate,up,down}_proj` | 28 × 7 = 196 |
| **Lv3: 音色条件付け** | 上記 + `vae2llm` / `llm2vae` + **新設 zero-init 注入層** | §2.4 |

コミュニティ実装が報告している「CLIP branch で 112 projections、MODEL branch で 114/114」
という数字は、**28層 × 4 (q,k,v,o) = 112** と **112 + `vae2llm` + `llm2vae` = 114** で
ぴったり一致する [実測 + コード]。つまりコミュニティの LoRA は
**attention のみを対象にし、MLP を外している**。MLP は1層あたり attention の3倍の
パラメータを持つので、**MLPを含めるだけで表現力は約3倍**になる。ここは素直な改善余地。

### 2.3 LoRAパラメータ数 [コード]

rank `r` のとき、対象行列 (in→out) あたり `r × (in + out)`。28層分の合計:

| rank | attention のみ<br>(28×4行列) | MLP のみ<br>(28×3行列) | attn + MLP<br>(28×7行列) | bf16 サイズ | NAR branch 比 |
|---:|---:|---:|---:|---:|---:|
| 8 | 3.21M | 5.51M | **8.72M** | 17.4 MB | 0.62% |
| 16 | 6.42M | 11.01M | **17.43M** | 34.9 MB | 1.24% |
| **32** | 12.85M | 22.02M | **34.87M** | **69.7 MB** | 2.47% |
| 64 | 25.69M | 44.04M | **69.73M** | 139.5 MB | 4.95% |
| 128 | 51.38M | 88.08M | **139.46M** | 278.9 MB | 9.90% |

**推奨 [推定]**: 単一話者の per-voice なら **r=32、attn + MLP、28層全部**(34.87M)。
データが30分未満なら r=16 に落とす。r=128 は 60分程度のデータでは過学習側に振れる。

内訳の目安として、`up_proj`/`gate_proj`/`down_proj` の3つで全体の63%を占める
(22.02M / 34.87M)。「まず軽く試す」なら **MLPのみ r=32 (22.02M)** から入るのが
コミュニティ実装との差分を作る最短ルート。

### 2.4 本命 — NARへの音色条件付け経路(zero-init 注入)

`nar_velocity()` の入力構成は以下のようになっている [コード: `modeling_yue2.py:637-666`]:

```python
token_emb = self.model.embed_tokens(tokens)              # [B, S, H]
latent_hidden_nar = self.vae2llm(x_nar.unsqueeze(0))     # [1, N_nar, H]  x_t を H 次元へ
latent_hidden_nar = latent_hidden_nar + time_emb         # timestep
latent_hidden_nar = latent_hidden_nar + pos_emb          # sinusoidal (非学習)
token_emb[0, nar_indices] = latent_hidden_nar[0]         # NAR位置に上書き
```

`hum-to-song` prosody adapter は、ここに**zero-init線形射影4本**でキャリア潜在を
加算する形をとっている(入力時 + layer 7/14/21 の直前)[実測]。同じ機構を
**サイン波キャリアではなく対象話者の実ボーカル潜在**で駆動するのが本命案。

| 注入層の設計 | パラメータ数 [コード] |
|---|---:|
| 4 × Linear(64 → 2048) — 参照潜在を直接射影 | **0.532M** |
| 4 × Linear(2048 → 2048) — 参照エンコーダ出力を射影 | **16.79M** |

**0.5M パラメータ**。LoRA本体(34.87M)よりさらに2桁小さい。zero-init なので
初期状態では素のモデルと数値的に完全一致し、**学習を回しても壊れない**のが利点。

ただし決定的な注意点がある。hum-to-song は**意図的に音色を落とした**キャリア
(サイン波)で学習されている。これを実ボーカルに差し替えると、同一セグメント同士を
ペアにした場合「参照をそのままコピーすれば損失が下がる」ショートカットが成立して
音色を学ばない。**cross-segment / cross-song ペアリング(参照は同一話者の別区間・別曲)が必須**。

### 2.5 学習コードを書くために必要な改造 [コード]

公式は推論専用なので、以下は自分で書く必要がある。**ここが最大のリスク項目**。

| 箇所 | 現状 | 必要な改造 |
|---|---|---|
| `nar_velocity()` | `@torch.no_grad()` デコレータ付き (`modeling_yue2.py:608`) | デコレータを外した学習用パスを別途用意 |
| 同 | `x_nar.unsqueeze(0)`, `nar_mask[0]`, `latent_hidden_nar[0]`, `token_emb[0, ...]` と **batch=1 前提** | バッチ次元の一般化(またはバッチ1 + 勾配累積で回避) |
| attention mask | `nar_velocity()` は `[B,1,S,S]` の**密行列**を実体化。S=24576 で fp32 2.25 GiB | **`nar.py` の `CachedNAR` を写せば mask は不要。** AR を causal で prefill して K/V をキャッシュし、NAR クエリを `cat(ar_k, nar_k)` に対してマスクなし全結合 attention で解けばハイブリッドマスクと等価。AR側K/Vは `t` ごとに再計算不要 |
| flow matching 損失 | 存在しない | `t` のサンプリングを推論側の `_shift_t_value`(sigmoid + `timestep_shift`)と整合させる。ここがズレるとアダプタが base と喧嘩する |
| 音声→semantic token | **未公開**(YuE Issues #141, #60) | コミュニティ tokenizer head v9 を使う。top-1 一致 18.9% / top-5 45.0% [実測] という精度で、これが上流のノイズ源になる |
| データ前処理 | `VAE.encode` は `[B, 2, S]` **48kHz ステレオ**を要求 (`modeling_vae.py:501`) | ソロボーカル(モノ)は複製してステレオ化。ただし §4.6 の領域ミスマッチに注意 |

## 3. 学習規模

### 3.1 シーケンス長の設計 — ここが費用を決める

NAR は自己回帰ではなくフローマッチングなので、**曲全体を入れる必要がない**。
ランダムな `t` と短い窓で学習できる。これが計算費用を劇的に下げる。

1フレーム = 1/25 秒 [コード: 48000 / 1920 = 25 Hz]:

| ボーカル長 | latent frames | 学習シーケンス長 S = ARプレフィクス + frames + 2 |
|---:|---:|---|
| 5 s | 125 | 約 600〜900 |
| 10 s | 250 | 約 750〜1,050 |
| **20 s** | **500** | **約 1,000〜1,300** |
| 30 s | 750 | 約 1,250〜1,550 |
| 60 s | 1,500 | 約 2,000〜2,300 |

ARプレフィクスは指示文 + `[Tags]` + `[Lyrics]` + ABC + semantic token を含み、
semantic token だけで窓と同じフレーム数を占める。**推奨は 20 秒窓 (S ≈ 1,000〜1,300)**。

参考: 推論時の1チャンクは `size = (24576 - prefix - 3) // 2` フレーム
[コード: `protocol.py:142`] で、プレフィクス500なら12,036フレーム = **約8分**。
つまり学習は推論の1/24の長さで済む。

### 3.2 メモリ [コード: パラメータ / [推定]: 活性]

固定費:

| 項目 | サイズ |
|---|---:|
| ベースモデル凍結 (3.580B × bf16) | **6.67 GiB** |
| LoRA r=16 (17.43M) + AdamW (bf16 + fp32 master + m + v) | 0.23 GiB |
| **LoRA r=32 (34.87M) + AdamW** | **0.46 GiB** |
| LoRA r=64 (69.73M) + AdamW | 0.91 GiB |
| zero-init 注入層 0.53M + AdamW | 0.01 GiB |

活性メモリ [推定: 1トークン1層あたり `10H + 4I` = 45,056 要素 = 88 KiB で概算]:

| S | batch | 勾配チェックポイント無し | **チェックポイント有り** | 密maskの追加分(fp32) |
|---:|---:|---:|---:|---:|
| 1,000 | 8 | 18.80 GiB | **2.38 GiB** | 0.03 GiB |
| 1,000 | 16 | 37.60 GiB | **4.76 GiB** | 0.06 GiB |
| 2,000 | 8 | 37.60 GiB | **4.76 GiB** | 0.12 GiB |
| 2,000 | 16 | 75.20 GiB | **9.52 GiB** | 0.24 GiB |
| 4,000 | 8 | 75.20 GiB | **9.52 GiB** | 0.48 GiB |

**帰結**: 勾配チェックポイントを入れれば **20秒窓 × batch 16 で 6.67 + 0.46 + 4.76 + 0.06 ≈ 12 GiB**。
40GB の A100 でも、**24GB の RTX 4090 でも入る**。
チェックポイント無しだと同条件で 45 GiB になり 80GB 級が必要。
[custom-training-plan.md](custom-training-plan.md) §6.1 の「80GB級が実質必須」は
**長窓・チェックポイント無し**を前提にした記述で、短窓設計ならこの制約は外れる。

**本プロジェクトはこれを根拠に、ローカルの RTX 4090(24GB)を主環境にしている。**
推論側も `StaticKVCache` が1トークン112 KiBなので、CFG 2分岐・context上限24,576でも
model込み 11.92 GiB で収まる([implementation-milestones.md](implementation-milestones.md) の実行環境節)。

### 3.3 スループット・ステップ数・費用

1トークンが通るのは片方の branch だけ(1.409B)。勾配チェックポイント込みで
forward の約4倍の FLOPs とすると [推定]:

| 設定 | tok/step | TFLOP/step | H100 @40% | A100 @40% | **RTX 4090 @40%** |
|---|---:|---:|---:|---:|---:|
| S=1,000 × batch 8 | 8,000 | 90 | 0.23 s/step | 0.72 s/step | **1.37 s/step** |
| S=1,000 × batch 16 | 16,000 | 180 | 0.46 s/step | 1.45 s/step | **2.73 s/step** |
| S=2,000 × batch 8 | 16,000 | 180 | 0.46 s/step | 1.45 s/step | **2.73 s/step** |
| S=2,000 × batch 16 | 32,000 | 361 | 0.91 s/step | 2.89 s/step | **5.46 s/step** |

RTX 4090 の bf16 dense ピークは約165 TFLOPS で、H100(989)の約1/6、A100(312)の約1/2。

**1回の学習ラン (3,000 steps) の所要時間 [推定]**:

| 設定 | H100 | A100 | **RTX 4090(ローカル)** |
|---|---:|---:|---:|
| S=1,000 × batch 8 | **約 0.2 h** | 約 0.6 h | **約 1.1〜1.5 h** |
| S=1,000 × batch 16 | 約 0.4 h | 約 1.2 h | **約 2.3〜3.0 h** |
| S=2,000 × batch 8 | 約 0.4 h | 約 1.2 h | 約 2.3〜3.0 h |
| S=2,000 × batch 16 | 約 0.8 h | 約 2.4 h | 約 4.6〜6.1 h |

**クラウドなら1ランは1時間未満、$1〜3。ローカル4090なら1〜3時間だが$0。**
つまりこのプロジェクトの費用は「1回の学習」ではなく **試行回数** で決まり、
**試行回数の大半をローカルに寄せれば費用はほぼ消える**
([implementation-milestones.md](implementation-milestones.md) の実行環境節)。

| 内訳 [推定] | 回数/時間 | 費用 |
|---|---|---:|
| 実装のデバッグ(損失が下がるまで) | 20〜40ラン | $30〜120 |
| ハイパーパラメータ探索(rank / lr / 窓長 / `t` 分布) | 20〜40ラン | $30〜120 |
| データ前処理(VAEエンコード + tokenizer head 推論) | 数時間 × GPU | $10〜30 |
| 評価(1曲生成 = 数分 × 条件数 × シード数) | 20〜50 h | $40〜150 |
| **Lv2 到達までの小計** | | **$110〜420** |

これは [custom-training-plan.md](custom-training-plan.md) §5 の Phase 2 見積($150〜350)と整合する。

**ただし本プロジェクトの現行計画では、この $110〜420 の大半がローカル4090に移り $0 になる。**
現行の総額は M0〜M6 で **$90〜470**
([implementation-milestones.md](implementation-milestones.md))。
いずれにせよ**予算がボトルネックではなく、実装工数と評価設計がボトルネック**。

### 3.4 ハイパーパラメータの出発点 [推定 + 実測]

| 項目 | 値 | 根拠 |
|---|---|---|
| rank | 32 (attn + MLP 全196行列) | §2.3 |
| alpha | 32 (scale = 1.0) | 過学習しやすい小データでは scale を上げない |
| learning rate | 1e-4 → cosine decay、warmup 100 steps | LoRA の標準域。zero-init 注入層は 3e-4 まで上げてよい |
| batch | 16 × 20秒窓(勾配累積で実効) | §3.2 |
| steps | 1,000〜4,000、held-out 曲で early stop | §4.2 |
| `t` サンプリング | 推論の `_shift_t_value` と同じ sigmoid + `timestep_shift=1.0` | ここがズレると壊れる(§2.5) |
| dropout | 参照条件を 10% の確率で落とす(CFG 用) | 推論時に条件の強さを調整できるようにする |
| 推論側 | temperature 0.7〜0.85 / top_k 30〜50 / repetition_penalty 1.05〜1.1 | [実測] コミュニティ運用知見。既定の 1.2 は `penalty ** counts` なので歌唱には強すぎる |

## 4. 必要なデータセット量

### 4.1 学習対象ごとに必要量が全く違う

| 学習対象 | 学習の性質 | 必要データ [推定] |
|---|---|---|
| Lv1 AR LoRA(歌い方・日本語) | 系列モデリング。汎化が必要 | **10〜30分**(日本語歌唱は別途 数時間あると効く) |
| Lv2 NAR LoRA(per-voice) | **単一話者への意図的な過学習**。汎化不要 | **30〜60分** |
| Lv3 音色条件付け(単一話者) | 参照→音色の写像。話者内の汎化が必要 | **2〜3時間** |
| Lv3 音色条件付け(任意話者 zero-shot) | 話者間の汎化が必要 | **100時間級 / 数百話者** ← 予算外 |

本プロジェクトは **10分固定**なのでこの表のどれも満たさない。
§4.7.2 の「10分を学習データではなく条件入力として使う」方針に切り替える。

**個人利用で特定の1人を狙うなら Lv3 の zero-shot 版は捨てて良い。**
「参照音声を差し替えられる汎用機能」は諦め、対象話者に固定したアダプタを作る方が
同じ予算で遥かに良い結果になる。

### 4.2 Lv2(声質)の必要量 — ステップ数との関係 [コード: フレーム数 / [推定]: 必要量]

20秒窓・batch 8 として、1エポックに必要なステップ数:

| データ量 | 秒 | latent frames | 20秒窓の個数 | 1 epoch = ? steps | 3,000 steps = ? epochs |
|---:|---:|---:|---:|---:|---:|
| 5 分 | 300 | 7,500 | 15 | 1 | **1,600** ← 完全に過学習 |
| 10 分 | 600 | 15,000 | 30 | 3 | 800 |
| 20 分 | 1,200 | 30,000 | 60 | 7 | 400 |
| **30 分** | 1,800 | 45,000 | 90 | 11 | **270** |
| **60 分** | 3,600 | 90,000 | 180 | 22 | **136** |
| 120 分 | 7,200 | 180,000 | 360 | 45 | 67 |
| 300 分 | 18,000 | 450,000 | 900 | 112 | 27 |

フローマッチングは毎エポックで異なる `t` を引くため、AR の系列学習ほど
エポック数に敏感ではない。それでも:

- **最低ライン: 10分** — クリーンなソロボーカル、複数曲・複数キー。これ未満は推奨しない
- **推奨: 30〜60分** — 1,000〜3,000 steps で 45〜270 epochs。held-out 曲での早期停止が前提
- **十分: 2〜3時間** — per-voice としてはここで逓減。これ以上増やす価値は Lv3 に進むときに出る

**「1曲だけ」「1分だけ」では原理的に届かない。** 声域の端、母音別の音色、
息の多い/太い声など、話者の音色空間を張るサンプルが必要。

本プロジェクトの 10分(実効6〜7分)は**この表の最低ラインちょうど**。
窓長・容量・step数をすべて下げる必要があり、具体値は §4.7.3 / §4.7.6。

### 4.3 データの多様性要件 — 総量より重要

同じ60分でも、中身で結果が変わる [推定]:

| 軸 | 満たすべき条件 |
|---|---|
| 曲数 | **最低5曲、できれば10曲以上**。1曲だけだとその曲の編曲・ミックスを覚える |
| 音域 | 対象話者の最低音〜最高音をカバー。高音部の裏声/ミックスボイスは別の音色として扱われる |
| 強弱 | ささやき〜フルボイスまで。mf だけだと mf しか出なくなる |
| 母音 | 日本語5母音すべてが各音域に出現すること。カタカナ英語のみの曲に偏らせない |
| 録音条件 | **同一の収録・ミックス条件で揃える**。曲間でEQ/リバーブが違うと音色ではなくミックスを学ぶ |
| 長さの分布 | 20秒窓が取れる連続発声区間。ブレス毎に1秒で切れる素材は不利 |

### 4.4 コミュニティ実装の失敗の再解釈 [実測 + コード]

コミュニティの per-voice アダプタは MERT identity で
**stock 0.852 > adapter 0.846 / 0.847**、つまり素のモデルに勝てていない。
これを本文書の枠組みで見ると:

| 自己申告されている欠陥 | 本文書での評価 |
|---|---|
| 実効データ量 **77〜330秒** | §4.2 の「最低ライン10分」の 1/8 〜 1/5。**そもそも足りない** |
| AR trainer が各シーケンスの**先頭ウィンドウのみ**を loss に通す | 実効データ量がさらに減る。上記はその欠陥後の値 |
| 300〜600 steps | 77秒データ・batch4×10秒窓換算で **156〜312 epochs**、330秒でも 36〜73 epochs。データ量に対して過剰 |
| 評価が単一シードの MERT コサイン | 0.852 vs 0.846 の差 0.006 は**ノイズに埋もれる粒度**。負の結果として弱い |
| LoRA が **attention のみ**(112 = 28×4) | MLP を外している。§2.2 の通り表現力の63%を使っていない |

**結論: 「効かなかった」ではなく「効いたか判定できる条件ではなかった」。**
データを10分以上に増やし、MLPを含め、held-out 曲 + 複数シード + 話者照合で測れば、
結果は変わり得る。これが独自実装に意味がある根拠。

### 4.5 ソロボーカル vs フルミックス — 見落としやすい領域ミスマッチ

**YuE2 が生成するのはフルミックス(伴奏込み)であって、ソロボーカルではない。**
`VAE.encode` は `[B, 2, S]` の 48kHz **ステレオ**を要求する [コード: `modeling_vae.py:292-293,501`]。

したがって学習データの作り方に3つの選択肢があり、それぞれ副作用が違う [推定]:

| 方式 | 内容 | 副作用 |
|---|---|---|
| **A: ソロボーカルのみ** | 分離したボーカルをモノ→ステレオ複製してVAEエンコード | NARが「伴奏なし・センター定位」の潜在分布を学び、推論時のフルミックス分布から外れる。伴奏が薄くなる/消える副作用が出やすい |
| **B: フルミックスのみ** | 対象話者の楽曲をそのままエンコード | 分布は合うが、音色が編曲・ミックスと不可分に学習される。別ジャンルを指定すると崩れる |
| **C: 混合(推奨)** | 対象を教師信号(§2.4 の注入参照側)にソロボーカル、**再構成ターゲットにはフルミックス**を使う | 実装は重いが、分布と音色分離の両方を満たす。参照側だけモノでよい |

**方式Cが本命。** 注入経路(§2.4)は「参照=ソロボーカル、ターゲット=フルミックス」という
非対称なペアを自然に扱えるので、zero-init 注入案と方式Cは相性が良い。
方式Aだけで走らせて「伴奏が消える」と悩むのは、実装前に避けられる失敗。

### 4.6 データの入手 — 手元の資産との対応

| 必要なもの | 手元の状況 |
|---|---|
| 日本語歌唱コーパス | `jaCappella`(HFキャッシュに ref のみ、音声は未ダウンロード)。アカペラ多パートなのでソロボーカルが直接取れる = 方式Aの素材に最適 |
| 対象話者のボーカル | **4〜6曲・約10分で確定、追加不可。** 一般論の推奨(30〜60分)を下回るため §4.7 の設計に切り替える |
| ボーカル分離 | 未確認。フルミックスから起こすなら別途必要 |
| 評価: ASR(PER用) | `whisper-large-v3` / `faster-whisper-large-v3` / `parakeet-tdt_ctc-0.6b-ja` / `anime-whisper` / `Qwen3-ASR-1.7B` — **4パスPERに十分揃っている** |
| 評価: 話者照合 | `pyannote/wespeaker-voxceleb-resnet34-LM` — **Lv3の判定に使える** |

対象話者の音源量は確定したので、**最初に確認すべき単一の項目は「歌唱区間の実秒数と
F0 × 母音の被覆」**(G0、$0)に移る。ここで決まる使用可能音域が、
§4.7.4 の `abc` による旋律拘束と、以降のすべての判断の前提になる。

### 4.7 本プロジェクトの実際の制約 — 対象話者データが10分・4〜6曲で固定

**確定した制約**: 対象話者の歌声は **4〜6曲・合計約10分**。**追加取得は不可**。
以下はこの条件を所与としたときの設計。§4.2〜§4.3 の推奨値(30〜60分・5〜10曲)を
満たせないので、**方針そのものを変える**。

#### 4.7.1 実効量 — 「10分」は10分ではない [コード: フレーム数]

4〜6曲で計10分なら1曲2分台、つまりフルソングの尺。無音・伴奏のみ区間を除くと:

| 何を数えるか | 秒 | latent frames | 潜在値の個数 |
|---|---:|---:|---:|
| 音声そのまま | 600 | 15,000 | 0.960M |
| **歌唱区間のみ(60〜70%想定)** | **390** | **9,750** | **0.624M** |
| さらに20秒連続が取れる区間のみ | 270 | 6,750 | 0.432M |

**実効は6〜7分**と見積もる。以下の数値はすべて実効390秒基準。
なお §4.4 のコミュニティ実効データは 77〜330秒なので、**実効ベースで1.2〜5倍、
素の音声長では2〜8倍**あり、「失敗が確定している水準」は超えている。

#### 4.7.2 最大の方針転換 — 10分を「学習データ」ではなく「条件入力」として使う

作るべきものは2つあり、**必要なデータの出所が異なる**。ここを分けるのが鍵。

| 作るもの | 学習内容 | 必要データ | 対象話者の10分を使うか |
|---|---|---|---|
| **A: 注入経路**(参照音声→音色の写像、§2.4) | 「参照から音色を読む」**機構そのもの** | **誰の歌声でもよい。多人数・多曲** | **使わない(1秒も)** |
| **B: 対象話者への適合** | この声、という**個別性** | 対象話者のみ | 使う |

**Aは対象話者のデータを一切必要としない。** 機構を他話者データで獲得しておけば、
対象話者の10分は学習セットではなく**推論時に差し込む参照音声**(パラメータ0)で足りる。

10分を 34.87M の LoRA で学習すると過剰度 **55.9倍**だが、条件入力として使う限り
過剰度という概念自体が消える。これがデータ固定下で最も効く一手。

Aの素材候補: **jaCappella**(HFキャッシュに ref あり。日本語・アカペラ・パート分離済みで
ソロボーカルが直接取れる)。ライセンスは **gated + 非商用限定**で、
YuE2重みの CC BY-NC 4.0 と個人利用の条件に矛盾しない。
ただし曲数・総時間は **viewer 無効で HF API から取得できなかったので、
ダウンロード時に実測が必要** [未検証]。

#### 4.7.3 容量 — 注入層を主役、LoRAは極小の補助

実効390秒 = 潜在値 0.624M に対する過剰度 [コード]:

| 構成 | パラメータ | 過剰度 |
|---|---:|---:|
| **zero-init 注入 4×(64→2048)** | **0.53M** | **0.9x** |
| **+ LoRA r=8 / MLPのみ / 14層** | **計 3.28M** | **5.3x** ← **推奨** |
| LoRA r=8 / MLPのみ / 28層 | 5.51M | 8.8x |
| LoRA r=8 / attn+MLP / 28層 | 8.72M | 14.0x |
| LoRA r=16 / attn+MLP / 28層 | 17.43M | 27.9x |
| ~~LoRA r=32 / attn+MLP / 28層~~(§2.3 の推奨) | 34.87M | **55.9x** |

**r を下げるより層を削る方が良い** [推定]。1層あたりの表現力を保ったまま総容量を落とせる。
層の選び方(前半/後半/等間隔)はアブレーションで決める。1ランが安い(§3.3)ので実測できる。

#### 4.7.4 被覆の穴は「埋める」のではなく「避ける」

データを足せない以上、F0や母音の被覆の穴は埋まらない。**生成側で踏まないようにする。**

ここで `SongRequest` の `abc` フィールドが使える [コード: `protocol.py:86` 定義、
`:99` 検証、`:122` エンコード]。**旋律を外部から与えられる公式機能**なので:

1. G0 で対象話者の実測音域を測る(半音ビンの F0 ヒストグラム)
2. 生成時は `cot="melody"` または `"full"` + `abc` 指定で、**旋律をその音域内に強制する**

これで「データに無い音域で崩れる」という10分固定の最大の弱点を、
学習ではなく**プロンプト側で**回避できる。伴奏生成やCFGの仕組みには手を入れない。

#### 4.7.5 増量の唯一の手段 — リミックス拡張

データが固定なので必須になる [推定]。

| やる | やらない |
|---|---|
| 分離ボーカルを**異なる伴奏・音量バランス・パン**で再ミックスし、音色を固定したままミックス条件を増やす。§4.5 の領域ミスマッチにも同時に効く | **ピッチシフト・フォルマント変換・EQ変更**。音色そのものを書き換えるため話者性の学習では逆効果 |
| 時間伸縮 ±5% まで | 時間伸縮の大幅適用 |

#### 4.7.6 学習設定(10分固定版)

§3.4 の一般設定を上書きする項目:

| 項目 | 値 | 根拠 |
|---|---|---|
| 窓長 | **5秒**(125フレーム)、**ランダムオフセット** | 固定グリッドでは実効390秒で78個しかないが、オフセット自由なら **9,626通り**。`t` のランダム性も乗るのでサンプル数は枯れない |
| batch | 16(勾配累積 + 勾配チェックポイント) | §3.2 で約12 GiB |
| steps | **600〜1,500**(123〜308 epochs) | 3,000 steps は 615 epochs で明確に過学習域 |
| 正則化 | LoRA dropout 0.05〜0.1 + weight decay | 過剰度5.3倍でも小データなので必要 |
| 評価 | **leave-one-song-out(4〜6 fold)** | 曲数が少なく、held-out 1曲固定ではその曲のクセに支配される |
| ペアリング | Aの学習は **cross-song 必須** | 同一区間ペアだとコピーで損失が下がり音色を学ばない(§2.4) |

**LOO-CV のコスト [推定]**(窓5s・batch16・約0.15 s/step、H100 $2.5/h):

| 構成 | 所要 | 費用 |
|---|---:|---:|
| 4 fold × 600 steps | 0.10 h | **$0.25** |
| 5 fold × 1,500 steps | 0.31 h | $0.78 |
| 6 fold × 1,500 steps | 0.38 h | $0.94 |

小データで「効いたか」を信頼できる形で測る唯一の方法。単一 held-out・単一シードだと
§4.4 の「差0.006がノイズに埋もれる」状態を再演する。

#### 4.7.7 期待値の再設定

| Lv | §1 の見込み(30〜60分) | **10分固定での見込み** |
|---|---|---|
| Lv1 歌い方・発音・日本語ディクション | 高い | **高い。** 10分で足りる領域 |
| Lv2 声質が同系統 | 中 | **中の下。** 生成時の音域・テンポ・ジャンルを訓練曲に寄せることが**前提条件**になる |
| Lv3 話者照合で本人判定 | 低〜中 | **対象外。** Aが想定以上に効いた場合のみ再検討 |

**Lv2を「訓練曲に近い音域・テンポ・ジャンルの範囲内でなら声質が寄る」という
条件付きの達成として定義し直す**のが、10分固定での正しいゴール設定。
**その「条件」の確定版は §6(operating envelope)。**
無条件のLv2を目標に置くと期待値を外す。
ジャンル一致の効果は [実測] 0.909(一致)vs 0.885(不一致)で裏付けがある。

|---|---|---|---:|---|
| **G0** | 歌唱区間の**実秒数**を測る。F0半音ビン × 母音のセル被覆を数える。評価ハーネス(4パスPER + 話者照合)を組み、**素のYuE2のベースラインを分散込みで取る** | 対象10分 | **$0** | 実効秒数と使用可能音域が確定。§4.7.4 の `abc` 拘束に使える音域表ができている |
| **G0.5** | **参照音声ICL注入**(§2.4 / [custom-training-plan](custom-training-plan.md) §4)。tokenizer head v9 で対象話者のトークンを取り AR文脈に prepend。**学習なし** | 対象10分(参照として) | $0〜50 | 話者照合コサインがベースライン + **2σ以上**。ここで効けば A/B の大半が不要 |
| **A** | **注入経路を他話者データで学習**(cross-song ペア、§4.7.2) | jaCappella 等。**対象話者は使わない** | $80〜250 | **学習に使っていない話者**で、参照を差し替えると音色が変わる |
| **B** | 対象話者へ適合(注入 0.53M + LoRA r=8 / MLPのみ / 14層 = 計3.28M、§4.7.3) | 対象10分 | $20〜60 | **LOO-CV 全fold平均**で stock を上回る。PER が悪化していない |
| **C** | 日本語ディクション AR LoRA(full temporal coverage) | 対象10分 + 日本語歌唱コーパス | $150〜300 | 4表記のうち最良の表記で PER が素のモデルより改善 |

**成果物が重みである(§0.1)ため、G0.5 が効いた場合でも A / B は省略できない。**
ICLは学習を伴わず重みが残らないので、G0.5 は「A/Bの設計を絞り込むための偵察」であって
代替ではない。ただしG0.5が効けば、Aの学習目標が「機構をゼロから作る」から
「効いた注入の効き方を重みに固定する」に変わり、A/Bのリスクは大きく下がる。

**G0 は $0 で、かつ以降の全判断の前提を決めるので、ここから始める。**
G0.5 も学習不要なので、**10分を学習に投入する前に、投入せずに済むかを先に確かめる**順序。
G0 + G0.5 + A + B の合計は **$100〜360** で、予算 $500〜1000 に対して C まで含めても余裕がある。

## 6. 達成条件(operating envelope)— 2026-09-18 合意

§4.7.7 の「条件付きの達成」の**条件を確定させたもの**。
成果物が学習コード + アダプタ重みである(§0 の成果物定義)ため、
**この節はそのまま配布時の model card の「動作範囲」になる。**
重みだけを条件抜きで配ると、範囲外で使われて「効かない」と評価されるため、
条件表は成果物の一部として扱う。

条件は性質が4種類あり、扱いが違う。

### 6.1 A: 生成時に守る条件(制御できる)

| # | 条件 | 具体値 | 根拠 |
|---|---|---|---|
| **A1** | **旋律を実測F0範囲内に収める** | G0で確定する半音レンジ内。`SongRequest.abc` で旋律を外部指定して拘束する | 手段は **[コード]** `protocol.py:86` 定義 / `:99` 検証 / `:122` エンコード。必要性は [推定] |
| **A2** | **タグ・ジャンルを訓練曲と揃える** | 同系統のタグを使う | **[実測]** ジャンル一致 0.909 vs 不一致 0.885 |
| **A3** | **曲の長さを8分未満に収める** | ARプレフィクス500tokで1チャンク = **12,036フレーム = 8.02分**。超えると2チャンクに割れ、チャンクごとに再prefillされるため境界で音色が動く | **[コード]** `protocol.py:142` |
| **A4** | **サンプリングを歌唱向けに落とす** | temperature 0.7〜0.85 / top_k 30〜50 / repetition_penalty **1.05〜1.1** | **[実測]** 既定 1.2 は `penalty ** freq`(`sampling.py:22`)なので歌唱には強すぎる |
| **A5** | **複数シードから選ぶ** | 1発で出る前提を置かない。best-of-n を運用に組む | [推定]。公式ベンチも best-of-8 を別スコアとして分離している |

**A3 は本プロジェクトではほぼ無害**。対象曲が2分台なら生成も同程度の尺で1チャンクに収まる。

ARプレフィクス長ごとの1チャンク上限 [コード: `protocol.py:142`]:

| ARプレフィクス | 1チャンク | 秒 | 分 |
|---:|---:|---:|---:|
| 200 tok | 12,186 fr | 487.4 | 8.12 |
| 500 tok | 12,036 fr | 481.4 | **8.02** |
| 1,000 tok | 11,786 fr | 471.4 | 7.86 |
| 2,000 tok | 11,286 fr | 451.4 | 7.52 |
| 4,000 tok | 10,286 fr | 411.4 | 6.86 |

### 6.2 B: データ側で満たされている必要がある前提(G0で数値化)

「守る」ものではなく「**足りているか測る**」もの。すべて [推定] ベースで、G0($0)で数値になる。

| # | 前提 | 足りない場合に起きること |
|---|---|---|
| **B1** | 声区の被覆(地声・裏声・ミックスボイス) | データに無い声区は出ない。裏声が1曲も無ければ高音で別人になる |
| **B2** | 強弱の被覆 | mf しか無ければ mf しか出ない |
| **B3** | **母音 × 音域のセル被覆** | 穴のあるセルでそこだけ音色が崩れる。日本語5母音 × 半音ビンで数える |
| **B4** | ミックス条件の一貫性 | 4〜6曲でEQ/リバーブが違うと音色ではなく**ミックスを学ぶ**。全曲同一条件なら学習は安定するが、その条件に固定される |

**B1〜B3 は10分固定では埋められない。** ゆえに §4.7.4 の方針(埋めずに A1 で避ける)を採る。

### 6.3 C: 明示的に保証しない範囲

| # | 範囲外 |
|---|---|
| **C1** | 訓練曲から離れた音域・ジャンル・テンポ |
| **C2** | 話者照合で本人と判定される水準(§1 の Lv3) |
| **C3** | 日本語以外の言語 |
| **C4** | 8分超の曲での通し一貫性 |
| **C5** | 任意の参照音声を差し替えられる汎用機能(zero-shot 多話者)。100時間級が必要で予算外(§4.1) |

### 6.4 D: 条件の厳しさはゲートの成否で変わる

条件リストは固定ではない。どのゲート(§5.2)が通るかで緩む [推定]。

| 通ったゲート | 緩む条件 | 理屈 |
|---|---|---|
| **G0.5(ICL注入)が効く** | A1 / B1 / B2 / B3 が大幅に緩む | 学習ではなく参照音声から音色を読むので、10分に無い音域も参照側で補える可能性がある |
| **A(他話者データで注入経路を学習)が成功** | A1 / B1 / B3 が緩む | 「参照から音色を読む」機構が汎化すれば、対象話者データの穴を参照で埋められる |
| **B(対象話者への適合)だけ成功** | **何も緩まない** | 10分を直接学習しただけなので、データの穴はそのまま残る |

**条件が最も厳しいのは「Aが失敗してBだけ通った」ケース。** 逆に G0.5 か A が効けば実用範囲は大きく広がる。

### 6.5 この条件表の性質 — 予測であって測定結果ではない

| 条件 | 裏付け |
|---|---|
| A3(8分)、A1の実施手段 | **[コード]** |
| A2(ジャンル一致)、A4(サンプリング) | **[実測]**(コミュニティ由来) |
| A1の必要性、A5、B1〜B4、D の全部 | **[推定]** |

**「YuE2単体で特定話者の声を寄せた」実証は公式にもコミュニティにも存在しない。**
したがって「この条件を守れば寄る」という保証は誰も持っていない。
G0($0)で B1〜B3 が数値として確定し、G0.5 と B で「実際にどの条件が効いていたか」が判明する。

## 7. まとめ

1. **アーキテクチャ上、声を担当するのは NAR branch の 1.409B(全体の39.4%)だけ。**
   ここに r=32 の LoRA を attn + MLP 全196行列に差すと **34.87M パラメータ / bf16 69.7MB**。
   コミュニティ実装は attention のみ(112行列)なので、**MLPを含めるだけで表現力3倍**。
2. **学習規模は小さい。** NAR はフローマッチングなので20秒窓で学習でき、
   勾配チェックポイント込みで **約12 GiB**、3,000ステップが **H100で20分・$1未満**。
   費用は1ランではなく**試行回数**で決まり、Lv2到達まで **$110〜420**。
3. **一般論では対象話者のクリーンなボーカル 30〜60分、5〜10曲以上が必要。**
   最低ライン10分。コミュニティが失敗した実効77〜330秒はこの1/8〜1/5で、
   「効かない」証拠としては弱い。
4. **本プロジェクトは10分・4〜6曲で固定(追加不可)。** そのため方針を変える(§4.7):
   10分を学習データではなく**条件入力**として使い、注入経路の機構は**他話者データで学習**する。
   容量は **注入0.53M + LoRA r=8/MLPのみ/14層 = 計3.28M**(過剰度5.3倍)まで絞り、
   窓5秒・600〜1,500 steps・**leave-one-song-out**で判定する。
   被覆の穴は埋められないので `SongRequest.abc` で**旋律を実測音域内に拘束して回避**する。
5. **現実的な到達点は Lv2(声質が同系統)。** ただし10分固定では
   「訓練曲に近い音域・テンポ・ジャンルの範囲内でなら寄る」という**条件付きの達成**に再定義する。
   話者照合で本人判定される Lv3 は対象外とし、G0.5(参照音声ICL注入、$0〜50)が
   効くかどうかで再検討する。
6. **最大のリスクは予算ではなく実装。** 公式学習コードが無く、`nar_velocity()` の
   `@torch.no_grad()` / batch=1 前提 / 密attention mask を書き直し、
   `t` のサンプリングを推論側 `_shift_t_value` と整合させる必要がある。
7. **成果物は学習コード + アダプタ重み**(§0.1)。達成条件は §6 に確定させ、
   これをそのまま model card の動作範囲として重みに添付する。
   条件抜きで重みだけ配ると範囲外で使われて「効かない」と評価される。
8. **最初にやることは G0($0)。** 歌唱区間の実秒数と、F0半音ビン × 母音のセル被覆を数える。
   ここで決まる使用可能音域が、以降のすべての判断と生成条件の前提になる。
